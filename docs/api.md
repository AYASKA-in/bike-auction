# API reference (v1)

All errors are RFC 9457 `application/problem+json` with `code` and `requestId`. Every response has `X-Request-Id`.
Identity comes only from the session cookie; clients never send user ids or timestamps.

Resolves due start/close first.                                                                                                                                                                                     |

See `packages/contracts/src/ws.ts`.                                                                                                                                                                                                                                                                                                                                          |

Bid errors: `AUTH_REQUIRED` 401 · `FORBIDDEN` 403 · `NOT_FOUND` 404 · `BID_TOO_LOW` 409 (+`minNextBidMinor`) ·
`ALREADY_LEADING` 409 · `AUCTION_NOT_LIVE` / `AUCTION_ENDED` / `AUCTION_CANCELLED` 409 · `BID_UNREASONABLE` 422
(+`maxAcceptableMinor`) · `BID_INVALID_AMOUNT` 422 · `IDEMPOTENCY_KEY_REUSED` 422 · `VALIDATION_FAILED` 422 ·
`RATE_LIMITED` 429 (+`Retry-After`). A replayed key returns the _original_ outcome, including rejections.
A manual bid exactly equal to someone's earlier maximum is rejected `BID_TOO_LOW` (the earlier maximum takes that
amount; that automatic bid is committed). Maximum-bid errors: `BID_TOO_LOW` (below the minimum next bid),
`BID_UNREASONABLE` (above 3× the reference price or the auction ceiling), plus the auth/state/idempotency codes above.
The maximum itself never appears in any event, view for others, bid history, D1 row, admin view or log.

## My bids and watchlist (signed-in USER; admins 403; D1 read models; `Cache-Control: no-store`)

Contracts: `packages/contracts/src/me.ts` (strict: no user ids, pseudonyms or reserve amounts).

| Method & path                            | Notes                                                                                                                                                                                                                                          |
| ---------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /api/v1/me/bids?tab=&limit=&cursor` | `tab` = `leading` (default) · `outbid` · `won` · `lost`; `limit` 1–48 (default 24). → `{tab, items: MyBidCard[], nextCursor}`. Live tabs sorted ending-soonest, finished tabs most-recently-closed; keyset cursor bound to its tab (else 422). |
| `GET /api/v1/me/watchlist`               | `{items: (AuctionCard & {watchedAt})[]}`, newest first, whole list (≤ 100). Drafts never appear.                                                                                                                                               |
| `GET /api/v1/me/watchlist/ids`           | `{ids, max}`: for the Watch buttons' state.                                                                                                                                                                                                    |
| `PUT /api/v1/me/watchlist/:auctionId`    | Idempotent add → 204. Unknown/draft/malformed id → 404. 101st distinct auction → 409 `CONFLICT`. Origin guard (CSRF) + edge limit 30 / 10 s per user (`watch:` key on `BID_RATE_LIMIT`) → 429.                                                 |
| `DELETE /api/v1/me/watchlist/:auctionId` | Idempotent remove → 204 (also when it wasn't watched).                                                                                                                                                                                         |

**Tab rules** (status is the _effective_ status, like the catalogue: a due close counts as ended):

- _leads_: D1 keeps only the leader's pseudonym, so you lead iff your highest bid = current price **and** your
  last bid seq = the auction's newest bid seq in `auction_bids_rm`. Bids strictly increase and a leader can't
  outbid themselves, so exactly one bidder matches; both rows come from one atomic projection batch.
- `leading` = LIVE and leads · `outbid` = LIVE and not leading · `won` = ENDED, outcome SOLD and
  `winner_user_id` is you (until the close is projected, a leader with reserve met: the engine's own rule) ·
  `lost` = ended or cancelled and not won.

## WebSocket protocol v1

`GET /api/v1/auctions/:id/stream` (upgrade). Auth is the session cookie only: never a token in the URL. Origin is
checked (cross-site WebSocket hijacking). The socket's identity is fixed at connect time; reconnecting re-reads it.

Server → client: `hello {serverTime}`, `auction.snapshot {serverTime, view}` (on connect and on every resync;
`view.viewer` is personal), public events (`auction.scheduled|started|extended|cancelled|ended`,
`bid.accepted`) each with a contiguous `seq`, and `you.outbid` (only to the previous leader's sockets).
Day 7 (additive): `bid.accepted` carries `kind: "MANUAL" | "PROXY"`. One command may commit several bids (a manual
bid and the maximum that answers it); `you.outbid` is sent once, after the commit's last bid, to everyone who led
before or during it but not after (a leader whose maximum held is not notified; a countered manual bidder is). Owners
of automatic bids, and a user who sets a maximum, also get a personal `auction.snapshot` (their `viewer`, incl.
`myMaxMinor`), because their client did not place those bids.
Client → server: `{"type":"ping"}` (auto-answered `pong`, doesn't wake the object) and `{"type":"resync"}`
(fresh snapshot; the object also resolves a due start/close first). At most 30 client messages per socket per
minute; more closes the socket with 1008.

**Client rules** (`apps/web/src/lib/live-auction.ts`, `live-feed.ts`):

- Apply an event only if `seq === lastSeq + 1`; ignore older/duplicates; on a gap → "stale" → resync; no
  snapshot within 5 s → reconnect.
- An HTTP view (`GET /auctions/:id`) is applied only if its seq ≥ lastSeq.
- "You're leading" comes only from a snapshot/HTTP `viewer`, or from your own 201 bid response whose seq is the
  latest applied bid. A later bid by someone else while you led = outbid (even if `you.outbid` was lost).
- Reconnect: back-off 0.5 s → 30 s with jitter; "failed" after 6 tries (keeps retrying); offline → wait for
  `online`; tab visible / bfcache restore → reconnect now or resync; heartbeat ping every 20 s, 45 s of silence =
  dead socket.
- Local countdown reaching zero only triggers a resync; the auction ends when `auction.ended` (or a snapshot)
  says so.
- After every snapshot or seq jump, reload the newest bid page (`GET /auctions/:id/bids`) and merge by seq.

## Admin observability (Day 8; role ADMIN; read-only; `Cache-Control: no-store`)

Contracts: `packages/contracts/src/ops.ts` (strict). **Privacy decision:** admins see bidder _pseudonyms_
only — never user ids or e-mails — in ops and ledger views (data minimisation, DPDP). Hidden maxima and
reserve amounts never appear in these responses. Identifying a bidder (dispute) is an offline, audited
DB procedure, not an API.
